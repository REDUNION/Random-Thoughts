 Docker Compose (FastAPI + Redis in containers)
Architected comprehensive Docker Compose deployment workflow for Kamatera VPS

Good choice — here's the full setup, from a fresh Kamatera VPS to a running app.
Step 1: Initial server setup (once)

SSH into your VPS as root, then:
bash

# Update system
apt update && apt upgrade -y

# Create a non-root user (don't run everything as root)
adduser deploy
usermod -aG sudo deploy

# Basic firewall
apt install ufw -y
ufw allow OpenSSH
ufw allow 80
ufw allow 443
ufw enable

# Switch to your new user for everything else
su - deploy

Step 2: Install Docker + Docker Compose
bash

curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker $USER
newgrp docker   # refresh group without logging out

# Verify
docker --version
docker compose version

Step 3: Project structure

On your VPS (after cloning from GitHub):
bash

git clone https://github.com/yourname/yourapp.git
cd yourapp

Your repo should have:

yourapp/
├── app/               # your FastAPI code
├── requirements.txt
├── Dockerfile
├── docker-compose.yml
└── .env               # NOT committed to git

Dockerfile:
dockerfile

FROM python:3.12-slim

WORKDIR /code

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY ./app ./app

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

docker-compose.yml:
yaml

services:
  redis:
    image: redis:7-alpine
    restart: always
    volumes:
      - redis_data:/data
    command: redis-server --requirepass ${REDIS_PASSWORD}

  api:
    build: .
    restart: always
    depends_on:
      - redis
    env_file:
      - .env
    ports:
      - "127.0.0.1:8000:8000"   # only exposed to localhost, nginx will proxy it

volumes:
  redis_data:

Note ports: 127.0.0.1:8000:8000 — this keeps FastAPI reachable only from the VPS itself, not the open internet. Nginx will be the public-facing door.

.env (create manually on the server, never commit it):

REDIS_PASSWORD=some-strong-password
REDIS_URL=redis://:some-strong-password@redis:6379/0

In your FastAPI code, connect using REDIS_URL from env, with the hostname redis (the Docker Compose service name — Docker's internal DNS resolves it automatically).
Step 4: Run it
bash

docker compose up -d --build
docker compose ps        # check both containers are up
docker compose logs -f   # watch logs

Step 5: Nginx reverse proxy + SSL
bash

sudo apt install nginx certbot python3-certbot-nginx -y

/etc/nginx/sites-available/yourapp:
nginx

server {
    listen 80;
    server_name yourdomain.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

bash

sudo ln -s /etc/nginx/sites-available/yourapp /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl restart nginx
sudo certbot --nginx -d yourdomain.com   # free SSL, auto-renews

Step 6: Your day-to-day deploy flow

From now on, every deploy is just:
bash

cd yourapp
git pull
docker compose up -d --build

Want me to write you a GitHub Actions workflow that runs this automatically on git push to main, so you never have to SSH in manually again?

###########################################
name: Deploy to Kamatera VPS

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Deploy over SSH
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          port: 22
          script: |
            cd ~/yourapp
            git pull origin main
            docker compose up -d --build
            docker image prune -f
			
############################################

Step 1: Create the workflow file
In your local repo (or directly on GitHub), create .github/workflows/deploy.yml:GitHub Actions d
eploy workflow for FastAPI+Redis app to Kamatera VPSGitHub Actions deploy workflow 
for FastAPI+Redis app to Kamatera VPSGitHub Actions deploy workflow for FastAPI+Redis app to Kamatera 
VPSDoneChange ~/yourapp to your actual project folder name on the VPS.
Step 2: Generate a dedicated SSH key for GitHub
On your local machine (not the VPS):
bashssh-keygen -t ed25519 -f ~/.ssh/kamatera_deploy_key -N ""
This creates two files: kamatera_deploy_key (private) and kamatera_deploy_key.pub (public).
Step 3: Authorize that key on the VPS
Copy the public key to your VPS's deploy user:
bashssh-copy-id -i ~/.ssh/kamatera_deploy_key.pub deploy@your-vps-ip
Or manually: paste the contents of kamatera_deploy_key.pub into ~/.ssh/authorized_keys on the VPS.
Test it works:
bashssh -i ~/.ssh/kamatera_deploy_key deploy@your-vps-ip
Step 4: Add secrets to GitHub
In your GitHub repo → Settings → Secrets and variables → Actions → New repository secret, add three:
Secret nameValueVPS_HOSTyour VPS IP addressVPS_USERdeployVPS_SSH_KEYthe full contents of the private key file (kamatera_deploy_key, not .pub)
For VPS_SSH_KEY, on your local machine:
bashcat ~/.ssh/kamatera_deploy_key
Copy the whole output — including the -----BEGIN OPENSSH PRIVATE KEY----- and -----END----- lines — and paste as the secret value.
Step 5: Add the workflow to your repo
bashmkdir -p .github/workflows
# copy deploy.yml into .github/workflows/
git add .github/workflows/deploy.yml
git commit -m "Add auto-deploy workflow"
git push origin main
How you use it going forward
That's it — your workflow is now:

Work locally in Cursor (laptop or PC, doesn't matter which — git keeps them in sync).
git add . && git commit -m "..." && git push
GitHub Actions automatically SSHes into your VPS, pulls the latest code, and rebuilds/restarts the containers.
Check progress under your repo's Actions tab on GitHub — green checkmark means it deployed successfully, 
red X means something failed (click in to see the logs).

You never manually SSH in to deploy again — only for occasional debugging or server maintenance.
One tip: keep your VPS .env file managed manually (it's not in git, 
so pulls won't touch it) — only update it by hand when secrets/config actually change.
